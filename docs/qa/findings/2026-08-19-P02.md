# P02 — engine: ammo stat parsing and cybergun ammo fit
- **Date:** 2026-08-19
- **Pass doc commit:** 4b361b2
- **App commit:** fdcdd56
- **Environment:** in-app browser, python http.server

Not a scheduled pass run — two defects found while building an unrelated
feature (a weapon assigned to a hand, loaded with AP), reported by the user,
then traced, fixed, and given permanent coverage in `P02-engine-gear.md`
(P02-009, P02-010, new P02-010b, P02-010c).

### NEW-001 — FAIL (now fixed)
`RULES.ammoStatMods` (`static/rules.js`) never applied a numeric stat
adjustment for any ammo with more than one clause in its Effect text.

The function split on `,` to separate clauses, but every multi-clause ammo row
in `misc_gear` is period-separated — `"Pen +2. Barrier +1."`, not
`"Pen +2, Barrier +1"`. With no comma present, the whole string was tested as
ONE part against three anchored regexes; the trailing text past the first
clause (". Barrier +1.") broke every one of them, and the entire string fell
through to `notes` unparsed. `applyAmmoStats` then had nothing to apply, so
the weapon's own Pen/Barrier/Damage/Accuracy passed through unchanged.

Observed on the Overview: a Kalishnikov A-80 loaded with AP (`Pen +2. Barrier
+1.`) showed Pen 5 / Barrier 4 — its base, un-modified values — with no
`wpn-ammo-mod` styling anywhere on the row, despite the ammo picker correctly
showing "AP" selected and a note reading "AP: Pen +2. Barrier +1." The note
is why this went unnoticed: it repeats the raw prose the number should have
come from, so at a glance the row looks like it's telling you the right thing.

Checked every ammo row in the data (28 total, `misc_gear` Class starting
"Ammo") against the old code by hand: **every row with two or more clauses**
was affected — AP, Flechette, Explosive, API, Subsonic loads, Buckshot, HEI,
Tracer Rounds, AP/Razor, Explosive Tip, and the vehicle/drone mount rounds
sharing the same parser (Vehicle Autocannon HEI, Vulcan/Cannon rounds where
applicable). Single-clause ammo with no trailing punctuation-breaking text
(none exist in the data — even "Explosive" is `"Damage +1."` with a trailing
period) were *also* broken, just less visibly, since a single wrong number is
easier to miss than a whole set going untouched.

**Fix:** split on `/[,.]\s*/` instead of `,` alone. Verified: all 28 ammo rows
now parse to the exact numeric deltas/sets their Effect text describes, with
only genuinely non-numeric prose ("Range = S", "Starts fires", "Ignores
armor", …) left in `notes`. See P02-009/P02-010/P02-010b for the exact
before/after values on AP and Buckshot.

### NEW-002 — FAIL (now fixed)
Buckshot could not be loaded into any cybergun, including the Shotgun option
it exists for.

`AMMO_FITS["Buckshot"] = row => row.Type === "Shotgun"` — the same test a real
(non-implanted) shotgun passes. The synthetic weapon row `shOverview` builds
for a cybergun's ammo-fit and reload checks (`static/sheet.js`, inside
`cyberguns.forEach`) hardcoded `Type: "Cybergun"` on every cybergun regardless
of archetype, so this test read `false` for the Shotgun cybergun the same as
it did for the Palm Pistol, Forearm SMG and Heavy Pistol options — Buckshot
never appeared in any cybergun's ammo picker.

`Type: "Cybergun"` was doing two unrelated jobs at once: `AMMO_FITS` reading
it as the weapon's real archetype, and `firingModeControls` reading the exact
same field to gate the "implanted; not meant to be done mid-fight" reload
confirm. The two can't both be satisfied by one field's value — a real
archetype string ("Shotgun") can't also read as the literal marker
"Cybergun". The row also had no `"Firing modes"` at all, which meant
`RULES.weaponFiringModes` fell back to `["SS"]` for every cybergun regardless
of its actual Modes column, silently blocking Tracer Rounds (needs FA) from
ever fitting a cybergun either — not user-reported, found while fixing the
above and covered by the same repair since it's the same missing-field root
cause. No cybergun in the shipped data has FA in its Modes, so this one had
no visible symptom yet, but the mechanism was wrong regardless of today's
data.

**Fix:** the synthesized row now carries `Type: g.Type` (the cyberguns
table's own archetype string), a new `cybergun: true` flag for the
reload-confirm gate `firingModeControls` reads, and `"Firing modes": g.Modes`
so mode-gated ammo reads real data. The two `r.Type === "Cybergun"` checks in
`firingModeControls` became `r.cybergun`.

## Verified as correct (no block, listed because they had no prior coverage)

- The accuracy half of an ammo fix reaches the Fire button, not just the
  stat line: with the Shotgun cybergun's ammo swapped to Buckshot
  (base Acc 2, Buckshot `+2 Accuracy`), the roll title read
  `"...= 5 skill + Accuracy 4 = 9 limit dice"` and clicking Fire opened the
  roller with `dice: 9` — `weaponRollSpec`'s `acc` parameter was already
  correctly wired to the ammo-adjusted figure on every caller (personal
  weapons, cyberguns, underbarrels); the only reason it read wrong was that
  `ammoStatMods` handed it a wrong number to begin with.
- Firing-mode bonus dice (Burst Fire +3b) and ammo-adjusted Accuracy compose
  correctly in the same roll: Kalishnikov A-80 + AP + Burst Fire opened the
  roller with `dice: 9, bonus: 3`.
- The cybergun reload confirm ("cannot be reloaded during combat") still
  fires for a non-Reloadable cybergun once its magazine is actually short a
  round, and still does not fire for an ordinary personal weapon — regression
  spot-check after moving the gate from `Type` to `cybergun`.
- `reloadAllWeapons()` (issue #85, `fdcdd56`) still correctly leaves a
  cybergun's magazine untouched after this refactor — it was already scoped
  to `ownedWeapons()`, which cyberguns were never part of.
- Full ten-tab sweep across five finalized fixtures: 0 thrown errors, 0
  horizontal overflow, both before and after the fix.
