### P04-007 — FAIL

Expected: `restored` has two slots with the second empty. Got exactly that:

    { "before":   [{"spirit":"Terra Factorem","force":5,"favors":3},
                   {"spirit":"Pacha Mama","force":4,"favors":2}],
      "shrunk":   [{"spirit":"Terra Factorem","force":5,"favors":3}],
      "restored": [{"spirit":"Terra Factorem","force":5,"favors":3},
                   {"spirit":"","force":0,"favors":0}] }

This is the known data-loss bug, recorded as FAIL per the case's own
instruction: dropping the bond count truncates `play.bond_slots`, so the Pacha
Mama bond, its Force and its Favors are destroyed rather than hidden. Raising
the count back gives an empty slot.

Unchanged by this round's rulings — no JC covers it because it isn't a
judgement call, it's a bug. Reproduced on a clean load of
`speaker-spirits.json`.

**Resolved 2026-08-05.** `speaker.bonds` has exactly one writer, the chargen
stepper, so this is not reachable from play — but **← Back to Chargen** is a
supported round trip that promises play state survives, and one ▼ click there
was enough to lose a bond for good.

Chasing it turned up the larger bug underneath. `deriveExploitActions` walked
`play.bond_slots` unbounded and granted 2 Control exploit actions per entry,
never consulting `speaker.bonds`. The only thing keeping that honest was the
render-time truncation — so a character who dropped 2→1 kept **4** Control
exploits until some view repainted and trimmed the array. A derived number
whose value depended on which tab was last opened.

Fixed by inverting it: `RULES.speakerBondCount()` is now the single authority
(clamped 0–4, the four bonds the cost table sells), every consumer bounds
itself with it, and nothing trims the array. Dormant slots are held and
announced in the Magic card rather than deleted. Verified against the `dd45099`
engine: zero drift on all seven fixtures, and on a deliberately over-length
`bond_slots` the old engine returned 4 Control exploits at bonds 0/1/2 where
the new one returns 0/2/4.

P04-007 is now a correctness case and passes; the exploit count is pinned
separately by the new **P04-011**.
